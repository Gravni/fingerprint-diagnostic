# v4.5: финальное задание по одноразовому raw-сбору

Дата ревью: 2026-09-07.

## Граница задачи

Никаких новых функций компаратора, Excel/MD, админки или дополнительных ручных
прогонов сейчас не требуется. Цель — гарантировать, что единственный будущий
plain/anti-прогон сотрудников сохранит весь собранный raw и сможет завершиться
после сетевой неопределённости.

## Уже исправлено Codex в публичном core

В ветке `codex/v4.5-one-shot`:

1. `captureComplete` больше не становится `true`, если вместо массива
   `_measurements` сохранён только `_measurementsError`.
2. `captureComplete` требует завершённый permissioned manifest
   (`_phaseManifest.complete === true`).
3. Исключения `MediaStreamTrack.getSettings()`, `getCapabilities()` и
   `getConstraints()` больше не проглатываются: в raw остаётся типизированная
   строка с именем и сообщением ошибки.
4. UI считает `captureComplete=true, READY=false` терминальным сохранённым
   raw-сбором и не предлагает бессмысленно нажимать кнопку повторно. Строгий
   verdict `READY/NOT_READY` при этом не ослаблен.

Для этих случаев добавлены регрессии. Новый браузерный прогон для проверки этих
локальных изменений не нужен.

## P0-1: oversized raw фактически теряется через blobRef

Подтверждённая причина:

- `lib/fp-encode.mjs` создаёт `blobRef` с `stored:false`, если `encodeValue()`
  вызван без `blobSink`;
- probe сейчас вызывает encoder без такого sink;
- schema принимает `stored:false` как CURRENT;
- в уже имеющемся прогоне 2026-09-07 это затронуло шесть значений
  `window.globals` длиной примерно 19–20 КБ: остались SHA и короткий preview,
  а исходный список восстановить нельзя.

Что требуется в закрытой панели:

1. Сохранять полное содержимое каждого вынесенного blob вместе с записью
   контекста в SQLite.
2. Делать экспорт JSONL самодостаточным: получатель должен восстановить значение
   без доступа к панели или отдельному неизвестному хранилищу.
3. Проверять SHA-256, длину и encoding при записи и чтении.
4. `stored !== true`, отсутствующий blob, несовпадающий hash/length либо
   `complete !== true` должны запрещать `captureComplete` и давать `NOT_READY`.

Обязательный интеграционный тест: детерминированная строка минимум 20 000 байт
проходит цепочку probe → `/collect` → SQLite → JSONL export и восстанавливается
байт-в-байт; её SHA-256 совпадает на входе и после экспорта.

## P0-2: потерянный ACK терминального manifest не восстанавливается

Подтверждённая причина:

- probe повторяет `run-manifest`, если не получил ACK;
- `buildManifest()` при повторе формирует новый payload;
- SQLite сохраняет первый manifest и сразу закрывает capture;
- если commit прошёл, но HTTP 200 потерялся, повтор получает
  `409 capture-closed`; поздний обязательный контекст также уже нельзя дописать.

Что требуется в закрытой панели и probe:

1. Один раз заморозить manifest с устойчивым ID/hash и повторять те же байты.
2. Повтор идентичного manifest после commit должен идемпотентно вернуть тот же
   успешный ACK и не создавать вторую запись.
3. Отличающийся manifest для закрытого capture должен вернуть 409.
4. Не закрывать capture, пока сервер не подтвердил все обязательные контексты и
   сохранность всех blob.
5. После неопределённого ответа сначала восстанавливать состояние через
   `/side-status`, без повторного сбора permissioned-данных.

Обязательные интеграционные тесты:

- commit прошёл, ответ потерян → повтор возвращает тот же ACK 200, manifest в
  базе один;
- обязательный контекст отсутствует → manifest не закрывает capture, контекст
  можно дописать и затем завершить;
- конфликтующий manifest после закрытия → 409;
- `/side-status` восстанавливает подтверждение без повторного permissioned-сбора.

## Условие приёмки и остановки

После исправления этих двух P0 нужны только свежие автоматические тесты, diff и
commit SHA. Деплой и новый plain/anti-прогон не выполнять. Если тесты проходят,
сборщик замораживаем; анализ отпечатков начнётся только после получения полного
комплекта от сотрудников.
